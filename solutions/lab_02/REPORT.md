## Задание 1. Имена, ссылки и изменяемость

### Эксперимент A. Неизменяемый объект

**Прогноз:**  
После операции `a += 1` имя `a` будет ссылаться на новый объект `11`, а `b` продолжит ссылаться на старый объект `10`. Идентификатор `id(a)` изменится, `id(b)` — останется прежним.

**Фактический результат:**  
Прогноз полностью подтвердился.
- До `a += 1`: `a = 10, b = 10`, `id(a) == id(b)` → `True`
- После `a += 1`: `a = 11, b = 10`, `id(a) != id(b)` → `a is b` стало `False`

**Объяснение:**  
Числа в Python — неизменяемые объекты. Операция `a += 1` не может изменить существующий объект `10` (это запрещено природой `int`). Вместо этого интерпретатор создаёт новый объект `11` и связывает с ним имя `a`. Имя `b` при этом продолжает ссылаться на старый объект `10`, поэтому его значение не меняется.

### Эксперимент B. Изменяемый объект

**Прогноз:**  
После `second.append(30)` оба имени покажут `[10, 20, 30]`, потому что `first` и `second` ссылаются на один и тот же список.

**Фактический результат:**  
Прогноз подтвердился.
- До `append`: `first = [10, 20], second = [10, 20]`, `first is second` → `True`
- После `append`: `first = [10, 20, 30], second = [10, 20, 30]` — оба изменились

**После переназначения `second = [10, 20, 30]`:**
- `first == second` → `True` (значения одинаковые)
- `first is second` → `False` (это уже разные объекты)
- После `second.append(40)` → `first` остался `[10, 20, 30]`, а `second` стал `[10, 20, 30, 40]`

**Объяснение:**  
Когда мы написали `second = [10, 20, 30]`, мы создали НОВЫЙ список в памяти и связали с ним имя `second`. Теперь `first` и `second` смотрят на разные объекты, поэтому изменения одного не затрагивают другой.

### Схемы связей между именами и объектами

**До переназначения `second`:**
```
first ──┐
         ├──> [10, 20, 30]  (id: 0xAAA)
second ─┘
```
Оба имени ссылаются на один и тот же список.

**После переназначения `second = [10, 20, 30]`:**
```
first ────> [10, 20, 30]  (id: 0xAAA)

second ───> [10, 20, 30]  (id: 0xBBB)
```
Теперь это два разных объекта с одинаковым содержимым.

### Практическая задача. Конфигурации проекта

**Проблема простого присваивания:**
Когда мы написали `config_b = config_a`, мы не создали копию словаря — мы просто сделали ещё одну ссылку на тот же объект. Поэтому при изменении вложенных списков (`participants`, `run_params`) через `config_b` эти же изменения отразились и на `config_a`.

**Решение через `deepcopy`:**
Функция `copy.deepcopy()` рекурсивно создаёт копии всех вложенных объектов. В результате `config_c` стала полностью независимой от `config_a`:
- `config_a["participants"]` = `["Анна", "Борис", "Виктор"]`
- `config_c["participants"]` = `["Анна", "Борис", "Виктор", "Галина"]`

Все три `assert` прошли успешно, подтверждая независимость конфигураций.

### Вопросы для анализа

**1. Меняет ли присваивание `second = first` сам объект?**  
Нет. Присваивание в Python никогда не меняет объекты — оно только связывает имя с объектом. В данном случае имя `second` стало указывать на тот же список, на который уже указывало имя `first`. Сам объект списка остался прежним.

**2. Почему операция над неизменяемым объектом приводит к связыванию имени с другим объектом?**  
Потому что неизменяемые объекты (числа, строки, кортежи) физически не могут быть изменены после создания. Когда мы пишем `a += 1`, интерпретатор вынужден создать новый объект `11` и перенаправить на него имя `a`. Старый объект `10` остаётся в памяти (и на него всё ещё ссылается `b`), пока не будет удалён сборщиком мусора.

**3. Как определить, что два имени обозначают один объект?**
Есть два способа:
- `a is b` — возвращает `True`, если имена ссылаются на один и тот же объект.
- `id(a) == id(b)` — сравнивает уникальные идентификаторы объектов в памяти.
Важно: `a == b` для этой цели НЕ подходит, потому что проверяет равенство значений, а не идентичность объектов.

## Задание 2. Поверхностное и глубокое копирование

### Наблюдения после изменений

**После `original.append(["Databases", 5])`:**
- `original` и `alias` — одинаковые (оба получили новый элемент)
- `shallow` — НЕ получил новый элемент (внешний список у него свой)
- `deep` — НЕ получил новый элемент (у него вообще всё своё)

Идентификаторы внешних списков:
- `id(original) == id(alias)` — это один и тот же объект
- `id(shallow)` и `id(deep)` — разные

Идентификаторы первого вложенного списка `original[0]`:
- `id(original[0]) == id(alias[0]) == id(shallow[0])` — все три ссылаются на один и тот же вложенный список
- `id(deep[0])` — другой (deepcopy скопировал и вложенные объекты)

**После `original[0][1] = 3`:**
- `original`, `alias`, `shallow` — все показали `["Python", 3]`, потому что их первый вложенный список — это один и тот же объект
- `deep` — остался `["Python", 5]`, потому что у него своя копия вложенного списка

### Таблица сравнения способов копирования

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы |
|----------|----------------------|-------------------------|----------------------|
| Присваивание (`alias = original`) |  Нет | Нет | Нет, это просто ещё одно имя |
| Поверхностная копия (`original.copy()`) | Да | Нет | Частично: внешний список независим, но вложенные объекты общие |
| Глубокая копия (`copy.deepcopy()`) |  Да | Да | Полностью независима |

### Ошибочная матрица

```python
wrong_matrix = [[0] * 3] * 3
wrong_matrix[0][0] = 1
```

Результат:
```
[[1, 0, 0],
 [1, 0, 0],
 [1, 0, 0]]
```

**Что произошло:** Оператор `*` для списка не создаёт копии вложенных элементов — он просто делает несколько ссылок на один и тот же объект. В итоге все три "строки" матрицы — это один и тот же список `[0, 0, 0]` в памяти. Когда мы меняем `wrong_matrix[0][0]`, мы меняем этот общий объект, и изменения видны во всех "строках".

### Правильная матрица

```python
correct_matrix = [[0] * 3 for _ in range(3)]
correct_matrix[0][0] = 1
```

Результат:
```
[[1, 0, 0],
 [0, 0, 0],
 [0, 0, 0]]
```

**Почему работает:** List comprehension (`[... for _ in range(3)]`) на каждой итерации создаёт НОВЫЙ вложенный список. В итоге три строки — это три разных объекта в памяти, и изменение одной не затрагивает другие.

---

### Вопросы для анализа

**1. Чем поверхностная копия отличается от глубокой?**  
Поверхностная копия (`copy()` или `list.copy()`) создаёт новый внешний контейнер, но вложенные объекты в неё не копируются — туда попадают ссылки на те же объекты, что и в оригинале.  
Глубокая копия (`copy.deepcopy()`) рекурсивно копирует вообще всё: и внешний контейнер, и все вложенные объекты, и все объекты внутри них, и так далее. В результате получается полностью независимая структура.

**2. Почему глубокое копирование не следует применять автоматически ко всем объектам?**  
Потому что это дорого. `deepcopy` тратит много времени и памяти на рекурсивный обход всей структуры. Если плоский список чисел или строк (неизменяемые объекты), то `deepcopy` даст тот же результат, что и обычное присваивание, но в 10-100 раз медленнее. Кроме того, `deepcopy` не умеет копировать некоторые объекты (например, открытые файлы, сетевые соединения, объекты с кастомными `__reduce__` методами). Поэтому его стоит использовать только тогда, когда реально есть вложенные изменяемые объекты.

**3. В каких случаях достаточно поверхностной копии?**  
Когда плоская структура (список чисел, строк, кортежей — всё неизменяемое), или когда ты собираешься менять только внешний контейнер (добавлять/удалять элементы), но не трогать вложенные объекты.  
Типичный пример: передача списка в функцию, где функция может добавить или удалить элементы, но не должна менять исходный список.

## Задание 3. Подсчёт ссылок и время жизни объекта

### Эксперимент 1. Подсчёт ссылок

**Прогноз и фактические результаты:**

| Действие | Прогноз | Факт |
|----------|---------|------|
| После создания `data` | 2 | 2 |
| После `alias = data` | 3 | 3 |
| После `container = [data]` | 4 | 4 |
| После `del alias` | 3 | 3 |
| После `container.clear()` | 2 | 2 |

Прогноз полностью совпал с фактом.

**Почему `sys.getrefcount()` показывает на одну ссылку больше ожидаемого?**  
Функция `sys.getrefcount(data)` принимает объект как аргумент, и в момент вызова создаётся **временная ссылка** на этот объект (аргумент функции). Поэтому счётчик всегда показывает значение на 1 больше, чем "реальных" ссылок в программе. Это особенность реализации — сам вызов `getrefcount` уже является ссылкой.

**Какие инструкции увеличивают счётчик ссылок:**
- Присваивание (`alias = data`) — создаёт новую ссылку на объект.
- Помещение в контейнер (`container = [data]`) — список хранит ссылку на объект.
- Передача в функцию как аргумент (временная ссылка).
- Возврат из функции.

**Какие инструкции уменьшают счётчик:**
- `del имя` — удаляет имя из пространства имён.
- Переназначение имени (`data = something_else`) — старая ссылка отвязывается.
- Удаление элемента из контейнера (`container.clear()`, `del container[0]`).
- Выход из области видимости (функция завершилась — локальные имена исчезли).

**Почему `del alias` удаляет имя, а не объект?**  
В Python `del` работает только с **именами** (или элементами контейнеров), а не с объектами напрямую. Инструкция `del alias` говорит интерпретатору: "убери имя `alias` из пространства имён". Объект при этом не удаляется — он просто теряет одну из ссылок. Если счётчик ссылок становится равным нулю, объект становится недостижимым, и сборщик мусора (reference counting) его удаляет. Но сам `del` об этом ничего не знает — он просто убирает ярлычок.

### Эксперимент 2. Слабая ссылка

**Результаты:**
- Пока существует сильная ссылка `record`, `weak_record()` возвращает сам объект: `Record('alpha')`.
- После `del record` слабая ссылка возвращает `None` — объект был удалён.

**Почему слабая ссылка не продлевает время жизни объекта?**  
Слабая ссылка (`weakref.ref`) — это ссылка, которая **не учитывается** в подсчёте ссылок. Она позволяет получить доступ к объекту, пока тот существует, но не мешает сборщику мусора его удалить. Как только сильных ссылок не остаётся, объект удаляется, а слабая ссылка автоматически превращается в `None`. Это фундаментальное отличие от обычной (сильной) ссылки, которая удерживает объект живым.

**Где слабые ссылки полезны?**  
Классический пример — **кэширование**. Когда есть большой объект (например, изображение или результат тяжёлых вычислений), и надо его запомнить, чтобы не пересчитывать. Но если объект больше нигде не используется — зачем держать его в памяти? Слабая ссылка позволяет сказать: "держи этот объект в кэше, пока он нужен кому-то ещё, но если все от него отказались — просто выброси". 

### Практическая задача. Слабый реестр

**Результаты:**
- Изначально в реестре три записи: `['a', 'b', 'c']`.
- После `del obj_c` запись `'c'` автоматически исчезает — сильных ссылок на объект не осталось.
- После `del obj_b` остаётся только `'a'`.
- Объект `obj_a` всё ещё доступен через `registry['a']`, потому что сильная ссылка `obj_a` жива.

**Вывод:**  
`WeakValueDictionary` не управляет временем жизни объектов — он только "наблюдает" за ними. Как только на объект не остаётся сильных ссылок, запись в словаре удаляется автоматически. Это удобно для построения реестров, кэшей и метаданных, где не хочется искусственно удерживать объекты в памяти.

### Вопросы для анализа

**1. При каком условии подсчёт ссылок позволяет освободить объект?**  
Когда счётчик ссылок на объект достигает нуля — то есть ни одно имя, ни один контейнер, ни одна функция больше не ссылается на этот объект. В этот момент CPython немедленно (в большинстве случаев) освобождает память. Это основной механизм управления памятью в CPython.

**2. Всегда ли освобождение Python-объекта означает немедленный возврат памяти операционной системе?**  
Нет. Если в программе есть циклические ссылки (объекты ссылаются друг на друга), то простой подсчёт ссылок не сработает — нужен циклический сборщик мусора (`gc`), который работает по расписанию, а не мгновенно. Поэтому память может "висеть" некоторое время даже после того, как объекты стали недостижимы.

**3. Чем сильная ссылка отличается от слабой?**
- **Сильная ссылка** (обычное имя, элемент списка, атрибут объекта) — увеличивает счётчик ссылок и удерживает объект живым. Пока есть хотя бы одна сильная ссылка, объект не будет удалён.
- **Слабая ссылка** (`weakref.ref`, запись в `WeakValueDictionary`) — не увеличивает счётчик ссылок. Позволяет получить доступ к объекту, пока он существует, но не мешает его удалению. Как только сильных ссылок не остаётся, слабая ссылка превращается в `None`.

## Задание 4. Циклические ссылки и сборщик мусора

### Эксперимент 1. Цикл из двух списков

**Что произошло:**
- Создали два пустых списка `first` и `second`.
- `first.append(second)` — первый список получил ссылку на второй.
- `second.append(first)` — второй список получил ссылку на первый.
- Образовался **цикл**: `first → second → first`.

**Проверка через `is`:**
- `first[0] is second` → `True` (первый элемент `first` — это тот же объект, что и `second`)
- `second[0] is first` → `True`

**Состояние сборщика мусора:**
- Автоматический сборщик включён: `True`
- Пороги поколений: `(700, 10, 10)` — это стандартные значения CPython. Они означают: "запускай сборку поколения 0, когда количество аллокаций минус deallocation превысит 700; поколения 1 — когда в нём накопится 10 объектов из поколения 0; поколения 2 — аналогично для поколения 1".
- Счётчики поколений: показывают, сколько объектов "живёт" в каждом поколении прямо сейчас.

**После `del first` и `del second`:**
- Имена удалены из пространства имён.
- Но сами объекты списков **не удалены** — у каждого из них счётчик ссылок равен 1 (ссылка от другого списка).
- Обычный подсчёт ссылок (reference counting) здесь бессилен — он видит, что объекты "используются".

**После `gc.collect()`:**
- Сборщик мусора нашёл цикл, понял, что до этих объектов нельзя добраться из программы, и удалил их.
- Вернул количество собранных объектов (обычно 2 — два списка).

### Дополнительный эксперимент: отключённый gc

Когда мы отключили автоматический сборщик (`gc.disable()`) и создали 5 циклических структур, объекты "зависли" в памяти — обычный подсчёт ссылок их не удалял. После ручного `gc.collect()` все 5 циклов были собраны.

### Практическая задача. Граф из словарей

**Схема графа:**
```
A → B → C → A   (цикл из трёх узлов)
D               (независимый узел)
```

**Код:**
```python
node_a = {"name": "A"}
node_b = {"name": "B"}
node_c = {"name": "C"}
node_d = {"name": "D (независимый)"}

node_a["next"] = node_b
node_b["next"] = node_c
node_c["next"] = node_a
```

**Что произошло после удаления `node_a`, `node_b`, `node_c`:**
- Цикл A → B → C → A стал недостижимым из программы.
- `gc.collect()` собрал 6 объектов: 3 словаря + 3 строковых значения ключей "next" (или больше, в зависимости от реализации).
- Узел `node_d` остался жив, потому что на него есть сильная ссылка `node_d` в нашем коде.

**Вывод:** сборщик мусора удаляет только **недостижимые** объекты. Если на объект есть хоть одна сильная ссылка из "корней" программы (локальные/глобальные переменные), он остаётся жив, даже если участвует в цикле.

### Вопросы для анализа

**1. Как возникает циклическая ссылка?**
Циклическая ссылка возникает, когда два или более объекта ссылаются друг на друга (напрямую или через цепочку). Классические примеры:
- Список, содержащий сам себя: `a = []; a.append(a)`
- Два списка, ссылающиеся друг на друга (как в эксперименте)
- Словари, ссылающиеся друг на друга через значения
- Объекты классов с атрибутами, указывающими на другие объекты, которые ссылаются обратно

В таких ситуациях подсчёт ссылок не может удалить объекты, потому что у каждого из них счётчик ≥ 1.

**2. Почему объект с ненулевым счётчиком ссылок иногда может быть недостижим из программы?**
Потому что счётчик ссылок считает **все** ссылки, включая ссылки от других недостижимых объектов. Если группа объектов ссылается только друг на друга, и ни один из них не доступен из "корней" программы (глобальные переменные, стек вызовов, локальные переменные текущей функции), то вся группа недостижима, несмотря на ненулевые счётчики ссылок. Именно для таких случаев и нужен циклический сборщик мусора — он находит "островки" изолированных объектов и удаляет их.

**3. Зачем сборщик мусора разделяет отслеживаемые объекты по поколениям?**
Это оптимизация, основанная на **"гипотезе о слабых поколениях"** (weak generations hypothesis): большинство объектов живут очень недолго, и если объект пережил несколько сборок мусора, он скорее всего будет жить долго.

Поколения работают так:
- **Поколение 0** — новые объекты. Проверяется чаще всего (порог 700).
- **Поколение 1** — объекты, пережившие одну сборку. Проверяется реже (порог 10).
- **Поколение 2** — "старожилы". Проверяется совсем редко.

Это позволяет не тратить время на проверку долгоживущих объектов (например, глобальных конфигураций) при каждой сборке. Сборщик сначала быстро чистит поколение 0, и только если там накопилось много "выживших", переходит к более старым поколениям. В результате типичная сборка мусора работает очень быстро, а редкие полные сборки обрабатывают всё.

## Задание 5. Исследование потребления памяти

### Часть 1. Размер отдельных объектов

**Результаты измерений через `sys.getsizeof()`:**
- Пустой список: 56 байт
- Список из 10 чисел: 136 байт
- Кортеж из 10 чисел: 120 байт
- Строка из 10 символов: 59 байт
- Целое число: 28 байт
- Объект `None`: 16 байт

**Почему размер контейнера не включает полный размер объектов?** 
Контейнер (список, кортеж) хранит только **ссылки** (указатели) на объекты, а не сами объекты. Функция `sys.getsizeof()` показывает размер структуры контейнера — заголовок объекта + массив указателей, — но не включает размер объектов, на которые эти указатели ссылаются. Например, список из 10 целых чисел занимает 136 байт, но сами 10 объектов `int` (по 28 байт каждый) — это ещё 280 байт, которые не учитываются в размере списка. Это позволяет одному и тому же объекту находиться в нескольких контейнерах одновременно без дублирования.

### Часть 2. Рост списка

**Наблюдения:**
Размер списка увеличивается не после каждого `append()`, а скачками. Например:
- Длина 0 → размер 56 байт
- Длина 1 → размер 88 байт
- Длина 5 → размер 120 байт
- Длина 9 → размер 184 байт
- Длина 17 → размер 248 байт
- ... и так далее с определённым шагом.

**Увеличивается ли размер списка после каждого `append()`?**  
Нет. Python использует стратегию **over-allocation** (геометрический рост). При увеличении размера список выделяет память не точно под текущее количество элементов, а с запасом. Это позволяет избежать дорогостоящей операции перераспределения памяти при каждом добавлении элемента. В результате амортизированная сложность `append()` — O(1), хотя отдельные вызовы могут быть дорогими (когда происходит реальное перераспределение).

**Чем длина списка отличается от объёма выделенной памяти?**  
- **Длина** (`len(lst)`) — это количество элементов, которые реально хранятся в списке.
- **Размер** (`sys.getsizeof(lst)`) — это объём памяти, выделенный под массив ссылок. Размер всегда больше или равен длине, потому что Python резервирует место для будущих элементов. Разница между размером и длиной — это "свободное место" для будущих `append()`.

### Часть 3. Измерение через `tracemalloc` и `sys.getsizeof`

**Результаты работы утилиты `memory_report.py`:**

| Сценарий               | Элементов | Размер (байт) | Текущий (КБ) | Пиковый (КБ) |
|------------------------|-----------|---------------|--------------|--------------|
| `list(range(100_000))` | 100000    | 800056        | 3898.30      | 3898.30      |
| `range(100_000)`       | 100000    | 48            | 0.00         | 0.00         |

**Отношение размеров (по `sys.getsizeof`):** ~16 667x (800 056 байт против 48 байт).

**Важное замечание о `tracemalloc`:**  
В ходе эксперимента `tracemalloc` показал ~0 КБ для объекта `range(100_000)`. Это произошло не потому, что `range` не потребляет память, а из-за архитектурной особенности CPython:
- `tracemalloc` отслеживает только память, выделенную через **Python-аллокатор** (`pymalloc`).
- Объект `range` — это встроенный C-объект, который выделяет память через стандартный C-аллокатор (`malloc`), минуя Python-аллокатор. Поэтому `tracemalloc` его "не видит".

Для корректного измерения размера отдельных объектов (особенно встроенных C-типов) надёжнее использовать `sys.getsizeof()` напрямую. А `tracemalloc` лучше подходит для анализа сложных сценариев с множеством Python-объектов, где нужно найти "узкие места" по пиковому потреблению.

**Вывод:** `list(range(N))` материализует все N объектов сразу и тратит много памяти. `range(N)` — это **ленивый объект**, который хранит только правило получения значений (`start`, `stop`, `step`), а не сами значения. Поэтому он занимает минимум памяти (всего 48 байт), независимо от N.

### Итоговый анализ: 3 способа уменьшить потребление памяти

На основе экспериментов лабораторной работы можно выделить три основных способа оптимизации:

**1. Использовать ленивые последовательности вместо материализованных.**  
*Связь с экспериментом:* Часть 3 показала, что `range(100_000)` занимает 48 байт, а `list(range(100_000))` — 800 КБ. Для больших данных всегда предпочтительнее использовать генераторы `(x**2 for x in range(N))` или `range`, а не списки.

**2. Использовать кортежи (`tuple`) вместо списков (`list`), если данные не меняются.**  
*Связь с экспериментом:* Часть 1 показала, что кортеж из 10 чисел занимает 120 байт, а список — 136 байт. Кортежи неизменяемы, поэтому Python не резервирует для них дополнительное место (over-allocation) и тратит меньше памяти на заголовок объекта.

**3. Избегать избыточного копирования через `copy.deepcopy()`.**  
*Связь с экспериментом:* Задания 1 и 2 показали, что `deepcopy` рекурсивно создаёт копии всех вложенных объектов. Если полная независимость не требуется (например, данные только для чтения), достаточно поверхностной копии или передачи ссылки, что сэкономит и память, и процессорное время.

### Вопросы для анализа

**1. Почему размер контейнера не обязательно включает полный размер всех объектов, на которые он ссылается?**  
Потому что контейнер хранит только ссылки (указатели) на объекты, а не сами объекты. В CPython список — это структура с заголовком и массивом указателей. Каждый указатель занимает 8 байт (на 64-битной системе), но сам объект, на который он указывает, может быть любого размера. Это позволяет одному и тому же объекту быть в нескольких контейнерах одновременно без дублирования.

**2. Увеличивается ли размер списка после каждого `append()`?**  
Нет. Python использует стратегию over-allocation: при каждом увеличении размера список выделяет память с запасом. Это позволяет избежать перераспределения памяти при каждом добавлении элемента. В результате амортизированная сложность `append()` — O(1), хотя отдельные вызовы могут быть дорогими (когда происходит реальное перераспределение).

**3. Почему список резервирует место с запасом?**  
Чтобы обеспечить амортизированную O(1) сложность операции `append()`. Если бы список выделял память точно под текущее количество элементов, то каждый `append()` требовал бы перераспределения памяти и копирования всех элементов, что дало бы O(N) сложность. С over-allocation перераспределение происходит редко (логарифмически), и средняя стоимость `append()` становится константной.

**4. Чем длина списка отличается от объёма выделенной памяти?**  
Длина (`len(lst)`) — это количество элементов, которые реально хранятся в списке. Размер (`sys.getsizeof(lst)`) — это объём памяти, выделенный под массив ссылок. Размер всегда больше или равен длине, потому что Python резервирует место для будущих элементов (over-allocation). Разница между размером и длиной — это "свободное место" для будущих `append()`.
