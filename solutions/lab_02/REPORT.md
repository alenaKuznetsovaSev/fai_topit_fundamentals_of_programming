## Задание 1. Имена, ссылки и изменяемость

### Эксперимент A. Неизменяемый объект

**Прогноз:**  
После операции `a += 1` имя `a` будет ссылаться на новый объект `11`, а `b` продолжит ссылаться на старый объект `10`. Идентификатор `id(a)` изменится, `id(b)` — останется прежним.

**Фактический результат:**  
Прогноз полностью подтвердился.
- До `a += 1`: `a = 10, b = 10`, `id(a) == id(b)` → `True`
- После `a += 1`: `a = 11, b = 10`, `id(a) != id(b)` → `a is b` стало `False`

**Объяснение:**  
Числа в Python — неизменяемые объекты. Операция `a += 1` не может изменить существующий объект `10` (это запрещено природой `int`). Вместо этого интерпретатор создаёт новый объект `11` и связывает с ним имя `a`. Имя `b` при этом продолжает ссылаться на старый объект `10`, поэтому его значение не меняется.

### Эксперимент B. Изменяемый объект

**Прогноз:**  
После `second.append(30)` оба имени покажут `[10, 20, 30]`, потому что `first` и `second` ссылаются на один и тот же список.

**Фактический результат:**  
Прогноз подтвердился.
- До `append`: `first = [10, 20], second = [10, 20]`, `first is second` → `True`
- После `append`: `first = [10, 20, 30], second = [10, 20, 30]` — оба изменились

**После переназначения `second = [10, 20, 30]`:**
- `first == second` → `True` (значения одинаковые)
- `first is second` → `False` (это уже разные объекты)
- После `second.append(40)` → `first` остался `[10, 20, 30]`, а `second` стал `[10, 20, 30, 40]`

**Объяснение:**  
Когда мы написали `second = [10, 20, 30]`, мы создали НОВЫЙ список в памяти и связали с ним имя `second`. Теперь `first` и `second` смотрят на разные объекты, поэтому изменения одного не затрагивают другой.

### Схемы связей между именами и объектами

**До переназначения `second`:**
```
first ──┐
         ├──> [10, 20, 30]  (id: 0xAAA)
second ─┘
```
Оба имени ссылаются на один и тот же список.

**После переназначения `second = [10, 20, 30]`:**
```
first ────> [10, 20, 30]  (id: 0xAAA)

second ───> [10, 20, 30]  (id: 0xBBB)
```
Теперь это два разных объекта с одинаковым содержимым.

### Практическая задача. Конфигурации проекта

**Проблема простого присваивания:**
Когда мы написали `config_b = config_a`, мы не создали копию словаря — мы просто сделали ещё одну ссылку на тот же объект. Поэтому при изменении вложенных списков (`participants`, `run_params`) через `config_b` эти же изменения отразились и на `config_a`.

**Решение через `deepcopy`:**
Функция `copy.deepcopy()` рекурсивно создаёт копии всех вложенных объектов. В результате `config_c` стала полностью независимой от `config_a`:
- `config_a["participants"]` = `["Анна", "Борис", "Виктор"]`
- `config_c["participants"]` = `["Анна", "Борис", "Виктор", "Галина"]`

Все три `assert` прошли успешно, подтверждая независимость конфигураций.

### Вопросы для анализа

**1. Меняет ли присваивание `second = first` сам объект?**  
Нет. Присваивание в Python никогда не меняет объекты — оно только связывает имя с объектом. В данном случае имя `second` стало указывать на тот же список, на который уже указывало имя `first`. Сам объект списка остался прежним.

**2. Почему операция над неизменяемым объектом приводит к связыванию имени с другим объектом?**  
Потому что неизменяемые объекты (числа, строки, кортежи) физически не могут быть изменены после создания. Когда мы пишем `a += 1`, интерпретатор вынужден создать новый объект `11` и перенаправить на него имя `a`. Старый объект `10` остаётся в памяти (и на него всё ещё ссылается `b`), пока не будет удалён сборщиком мусора.

**3. Как определить, что два имени обозначают один объект?**
Есть два способа:
- `a is b` — возвращает `True`, если имена ссылаются на один и тот же объект.
- `id(a) == id(b)` — сравнивает уникальные идентификаторы объектов в памяти.
Важно: `a == b` для этой цели НЕ подходит, потому что проверяет равенство значений, а не идентичность объектов.


## Задание 2. Поверхностное и глубокое копирование

### Наблюдения после изменений

**После `original.append(["Databases", 5])`:**
- `original` и `alias` — одинаковые (оба получили новый элемент)
- `shallow` — НЕ получил новый элемент (внешний список у него свой)
- `deep` — НЕ получил новый элемент (у него вообще всё своё)

Идентификаторы внешних списков:
- `id(original) == id(alias)` — это один и тот же объект
- `id(shallow)` и `id(deep)` — разные

Идентификаторы первого вложенного списка `original[0]`:
- `id(original[0]) == id(alias[0]) == id(shallow[0])` — все три ссылаются на один и тот же вложенный список
- `id(deep[0])` — другой (deepcopy скопировал и вложенные объекты)

**После `original[0][1] = 3`:**
- `original`, `alias`, `shallow` — все показали `["Python", 3]`, потому что их первый вложенный список — это один и тот же объект
- `deep` — остался `["Python", 5]`, потому что у него своя копия вложенного списка

### Таблица сравнения способов копирования

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы |
|----------|----------------------|-------------------------|----------------------|
| Присваивание (`alias = original`) |  Нет | Нет | Нет, это просто ещё одно имя |
| Поверхностная копия (`original.copy()`) | Да | Нет | Частично: внешний список независим, но вложенные объекты общие |
| Глубокая копия (`copy.deepcopy()`) |  Да | Да | Полностью независима |

### Ошибочная матрица

```python
wrong_matrix = [[0] * 3] * 3
wrong_matrix[0][0] = 1
```

Результат:
```
[[1, 0, 0],
 [1, 0, 0],
 [1, 0, 0]]
```

**Что произошло:** Оператор `*` для списка не создаёт копии вложенных элементов — он просто делает несколько ссылок на один и тот же объект. В итоге все три "строки" матрицы — это один и тот же список `[0, 0, 0]` в памяти. Когда мы меняем `wrong_matrix[0][0]`, мы меняем этот общий объект, и изменения видны во всех "строках".

### Правильная матрица

```python
correct_matrix = [[0] * 3 for _ in range(3)]
correct_matrix[0][0] = 1
```

Результат:
```
[[1, 0, 0],
 [0, 0, 0],
 [0, 0, 0]]
```

**Почему работает:** List comprehension (`[... for _ in range(3)]`) на каждой итерации создаёт НОВЫЙ вложенный список. В итоге три строки — это три разных объекта в памяти, и изменение одной не затрагивает другие.

### Вопросы для анализа

**1. Чем поверхностная копия отличается от глубокой?**  
Поверхностная копия (`copy()` или `list.copy()`) создаёт новый внешний контейнер, но вложенные объекты в неё не копируются — туда попадают ссылки на те же объекты, что и в оригинале.  
Глубокая копия (`copy.deepcopy()`) рекурсивно копирует вообще всё: и внешний контейнер, и все вложенные объекты, и все объекты внутри них, и так далее. В результате получается полностью независимая структура.

**2. Почему глубокое копирование не следует применять автоматически ко всем объектам?**  
Потому что это дорого. `deepcopy` тратит много времени и памяти на рекурсивный обход всей структуры. Если плоский список чисел или строк (неизменяемые объекты), то `deepcopy` даст тот же результат, что и обычное присваивание, но в 10-100 раз медленнее. Кроме того, `deepcopy` не умеет копировать некоторые объекты (например, открытые файлы, сетевые соединения, объекты с кастомными `__reduce__` методами). Поэтому его стоит использовать только тогда, когда реально есть вложенные изменяемые объекты.

**3. В каких случаях достаточно поверхностной копии?**  
Когда плоская структура (список чисел, строк, кортежей — всё неизменяемое), или когда ты собираешься менять только внешний контейнер (добавлять/удалять элементы), но не трогать вложенные объекты.  
Типичный пример: передача списка в функцию, где функция может добавить или удалить элементы, но не должна менять исходный список.
