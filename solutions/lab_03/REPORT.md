### Часть 1. Проверка диапазонов

Программа сначала проверяет, что `score` находится в диапазоне `[0, 100]`, а `absences` — в `[0, 5]`. Если хотя бы одно значение некорректно, выводится сообщение об ошибке, и дальнейшая классификация не выполняется. Реализовано через паттерн **guard clause** (ранний выход):

```python
if not (0 <= score <= 100):
    print(f"Ошибка: результат {score} вне допустимого диапазона [0, 100].")
    sys.exit(1)

if not (0 <= absences <= 5):
    print(f"Ошибка: количество пропусков {absences} вне допустимого диапазона [0, 5].")
    sys.exit(1)
```

Такой подход уменьшает вложенность кода и соответствует принципу "flat is better than nested" из Zen of Python. Программа завершается с кодом возврата `1`, сигнализируя операционной системе об ошибке.

### Порядок проверки условий и недостижимые ветви

**Порядок проверки:**
1. Сначала проверяется валидность диапазонов (`score` и `absences`). Если хоть одно значение некорректно — программа завершается через `sys.exit(1)` с ненулевым кодом возврата.
2. Затем определяется базовый уровень через каскад `if / elif / else`.
3. Потом проверяется условие понижения (`absences > 3`).
4. Наконец, через `match / case` формируется описание типа работы.

**Недостижимые ветви:**
Если бы мы переставили условия в каскаде уровня, некоторые ветви стали бы недостижимыми. Например, если написать:

```python
if score >= 60:
    level = "удовлетворительный"
elif score >= 75:  # ← НЕДОСТИЖИМАЯ ВЕТВЬ
    level = "хороший"
```

То ветка `score >= 75` никогда не выполнится, потому что все значения `>= 75` уже пойманы первой веткой `>= 60`. Поэтому важен порядок: от большего к меньшему (или от меньшего к большему, но с правильными условиями).

В нашей реализации порядок корректный: `>= 90`, затем `>= 75`, затем `>= 60`, иначе — недостаточный. Каждая ветвь достижима.

### Когда использовать `if/elif`, а когда `match/case`

В ходе выполнения задания стало понятно, что эти две конструкции не взаимозаменяемы — у каждой своя область применения.

**`if / elif` подходит для условий с диапазонами и сложной логикой** (например, `score >= 90`). Здесь важна проверка "больше/меньше", и `match/case` не даст преимуществ — он работает с точными значениями, а не с неравенствами.

**`match / case` идеален для дискретных значений и структурного сопоставления** (например, классификация по уровню, тип работы). Он читается как таблица соответствий и исключает ошибки порядка условий — все ветви равноправны.

В нашей программе это разделение применено последовательно: определение уровня через `if/elif` (диапазоны), а подсчёт и описание типа работы — через `match/case` (дискретные значения). Это правильное разделение ответственности.

### Линейный поиск

Реализован поиск первого вхождения с ранним выходом через `break`. Если число отсутствует — возвращается `-1`.

Тестовые сценарии:
- Поиск `18` → индекс 3 (первое вхождение), 4 сравнения
- Поиск `99` → индекс -1, 10 сравнений (прошли весь список)

### Проверка простоты

**Псевдокод алгоритма:**
```
function is_prime(n):
    if n < 2: return False
    if n == 2: return True
    if n % 2 == 0: return False
    divisor = 3
    while divisor * divisor <= n:
        if n % divisor == 0: return False
        divisor += 2
    return True
```

**Почему достаточно делителей до √n:**
Если число `n` составное, то его можно представить как `n = a * b`, где `a ≤ b`. Если оба делителя больше √n, то `a * b > n` — противоречие. Значит, хотя бы один делитель не превосходит √n. Поэтому достаточно проверить делители до √n включительно.

**Оптимизация:** после проверки делимости на 2 перебираем только нечётные делители (3, 5, 7, ...) — это вдвое сокращает число итераций.

### Альтернативный подход: Решето Эратосфена

В ходе выполнения задания возник вопрос: а что если нужно проверить простоту **многих чисел** в пределах одного диапазона? Перебор делителей для каждого числа отдельно будет неэффективен.

Решение — построить таблицу простых чисел сразу для всего диапазона. Алгоритм "Решето Эратосфена" работает так:

1. Создаётся булев массив размера N (где N — максимальное число).
2. Внешний цикл перебирает числа от 2 до √N. Если число не помечено как составное — оно простое.
3. Внутренний цикл помечает все кратные этому простому числу как составные.

**Реализация:**
```python
def sieve_of_eratosthenes(limit: int) -> list[bool]:
    """Строит таблицу: is_prime[i] == True, если i — простое."""
    is_prime = [True] * (limit + 1)
    is_prime[0] = is_prime[1] = False

    num = 2
    while num * num <= limit:
        if is_prime[num]:
            for multiple in range(num * num, limit + 1, num):
                is_prime[multiple] = False
        num += 1

    return is_prime
```

**Сравнение подходов:**

| Критерий | Единичная проверка (из задания) | Решето Эратосфена |
|----------|--------------------------------|-------------------|
| Сложность на одно число | O(√n) | O(1) после предподсчёта |
| Сложность на k чисел до N | O(k · √N) | O(N log log N) + O(k) |
| Память | O(1) | O(N) |
| Когда лучше | Мало чисел, большие значения (до 10¹⁸) | Много чисел, ограниченный диапазон |

**Вывод:** если нужно проверить одно большое число — используем перебор делителей до √n. Если нужно проверить много чисел в пределах одного диапазона — используем решето. В задании выбрана единичная проверка, так как функция должна работать для произвольного числа без знания диапазона.

### Оценки сложности

| Алгоритм | Временная сложность | Пространственная | От чего зависит |
|----------|---------------------|------------------|-----------------|
| Сумма / мин / макс / чётные | O(n) | O(1) | От длины списка |
| Подсчёт значений > среднего | O(n) | O(1) | От длины списка |
| Линейный поиск | O(n) (в худшем) | O(1) | От длины списка |
| Проверка простоты | O(√n) | O(1) | От значения числа |
| Решето Эратосфена | O(N log log N) | O(N) | От максимального числа |

**Дополнительная память:** во всех алгоритмах используется O(1), кроме сортировки выбором (создаёт копию списка — O(n)) и решета (таблица O(N)).

### Практическое расширение: сортировка и поиск

**Сортировка выбором — псевдокод:**
```
function selection_sort(arr):
    a = copy(arr)
    n = len(a)
    for i from 0 to n-1:
        min_idx = i
        for j from i+1 to n-1:
            if a[j] < a[min_idx]:
                min_idx = j
        swap(a[i], a[min_idx])
    return a
```

**Бинарный поиск — псевдокод:**
```
function binary_search(arr, target):
    left = 0
    right = len(arr) - 1
    while left <= right:
        mid = (left + right) // 2
        if arr[mid] == target: return mid
        elif arr[mid] < target: left = mid + 1
        else: right = mid - 1
    return -1
```

**Сравнительная таблица числа сравнений (худший случай — ищем отсутствующий элемент):**

| Размер | Сортировка выбором | Линейный поиск | Бинарный поиск |
|--------|--------------------|---------------|----------------|
| 10     | 45                 | 10            | 4              |
| 100    | 4950               | 100           | 7              |
| 1000   | 499500             | 1000          | 10             |

**Наблюдения:**
- Сортировка выбором: число сравнений растёт как n(n-1)/2 ≈ O(n²). При увеличении размера в 10 раз — рост в ~100 раз.
- Линейный поиск: O(n) — рост строго пропорционален размеру.
- Бинарный поиск: O(log₂ n) — при росте размера в 10 раз число сравнений увеличивается всего на ~3-4.

**Вывод:** бинарный поиск на 1000 элементах требует всего 10 сравнений против 1000 у линейного — разница в 100 раз. Именно поэтому для поиска в отсортированных данных всегда предпочтительнее бинарный поиск.

### Вопросы для анализа

**1. От какого параметра зависит число операций в каждом алгоритме?**

**3. Почему ограничение делителей квадратным корнем корректно?**

## Задание 3. Числовые типы, операции и преобразования


### Контрольные вопросы

**1. Почему результат обычного деления двух объектов `int` имеет тип `float`?**  
Это осознанный дизайн Python 3. Оператор `/` всегда возвращает `float`, чтобы избежать неожиданной потери точности. Например, `5 / 2` должно дать `2.5`, а не `2`. Если программисту нужно именно целочисленное деление, он явно использует оператор `//`. В Python 2 поведение было другим (`/` для `int` давал `int`), что приводило к частым ошибкам, поэтому в Python 3 это исправили.

**2. В чем отличие преобразования `int("42")` от `int(42.9)`?**  
Это два принципиально разных действия:
- `int("42")` — **парсинг строки**: интерпретатор читает текстовое представление числа и преобразует его в числовой объект. Если строка не является валидным числом (например, `"42abc"`), будет вызвано исключение `ValueError`.
- `int(42.9)` — **усечение (truncation)**: у вещественного числа просто отбрасывается дробная часть. Результат — `42`. Округления не происходит (для округления используется `round()`).

**3. Какие значения из эксперимента D являются falsy?**  
Falsy-значения (те, что при приведении к `bool` дают `False`):
- `bool(0)` → `False` (ноль — единственное falsy-число).
- `bool("")` → `False` (пустая строка — единственная falsy-строка).

Все остальные значения (`-1`, `"False"`, ненулевые числа, непустые строки) являются truthy.


## Задание 4. Строки, Unicode и форматирование


### Контрольные вопросы

**1. Почему `len(symbol)` и `len(symbol.encode("utf-8"))` могут различаться?**
- `len(symbol)` возвращает количество **символов** (Unicode code points) в строке. Для символа `"Я"` это `1`.
- `len(symbol.encode("utf-8"))` возвращает количество **байт**, необходимых для хранения этих символов в кодировке UTF-8. Кириллические символы в UTF-8 занимают по 2 байта, поэтому длина байтового представления равна `2`.

**2. Что означают границы и шаг в записи `text[start:stop:step]`?**
- `start` — индекс начала среза (включительно). По умолчанию `0` (или конец, если шаг отрицательный).
- `stop` — индекс конца среза (**не включительно**). По умолчанию длина строки (или начало, если шаг отрицательный).
- `step` — шаг выборки символов. По умолчанию `1`. Если `step` отрицательный (например, `-1`), срез идет в обратном направлении.

**3. Почему строка считается неизменяемым объектом, хотя методы вроде `.upper()` возвращают измененный текст?**
Методы строк (такие как `.upper()`, `.lower()`, `.replace()`) **не модифицируют исходный объект в памяти**. Вместо этого они создают и возвращают **новый объект** `str` с нужными изменениями, оставляя исходную строку нетронутой.

## Задание 5. Информационная карточка вычислительного эксперимента


### Контрольный вопрос

**Что изменится на уровне объектов и связывания имен при повторном присваивании?**

Сам объект не изменится — в Python числа неизменяемые. Изменится только "ярлычок": имя отвязывается от старого объекта и привязывается к новому. Например, если было `runs = 8`, а потом стало `runs = 10`, то объект `8` никуда не делся, просто имя `runs` теперь смотрит на объект `10`. А старый объект `8`, если на него больше никто не ссылается, со временем удалит сборщик мусора.

Например, 2 + 3 * 4 в байткоде превращается в готовую константу 14. Однако эта оптимизация работает только в рамках одного выражения и только с литералами — если в формуле участвуют переменные, вычисление происходит в момент выполнения. Это наглядно показало разницу между compile-time и runtime, которую я раньше не осознавала

2. **`0.1 + 0.2 != 0.3`.** До лабы я думала, что это какой-то баг питона, а оказалось, что это особенность двоичного представления дробей (стандарт IEEE 754). Теперь понятно, почему для `float` надо использовать `math.isclose()`, а не `==` в питоне.

3. **`is` и `==` — это разные вещи.** Поначалу казалось, что это одно и то же. А оказалось, что `==` сравнивает значения, а `is` — один ли это объект в памяти. И что `b = a` не копирует объект, а просто делает еще одну ссылку на него. Это важно помнить, особенно с учетом кеша малых целых и интернирования строк.
